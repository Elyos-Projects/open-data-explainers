# Toolkit Integration: Data-Currency Badges & Drift Detection

> Version: 1.0.0 · Status: Published · Last updated: 2026-07-24 · License: CC-BY-4.0

## Overview

This document specifies how the **data-currency badge component** and **drift-detection utilities** should be integrated into the shared explainer toolkit (toolkit-002). Both are cross-cutting concerns that apply to all explainers in the project.

---

## 1. Data-Currency Badge Component

### 1.1 Component Location (in toolkit-002)

When toolkit-002 is built, the badge component should be committed to:

```
packages/toolkit/
  src/
    components/
      data-currency-badge/
        DataCurrencyBadge.tsx      # React component (implementation)
        DataCurrencyBadge.css      # Styling (light & dark mode)
        DataCurrencyBadge.test.tsx # Component tests
        index.ts                   # Export
        README.md                  # Component documentation
```

### 1.2 Component Specification

The component accepts the following props:

```typescript
interface DataCurrencyBadgeProps {
  retrievalDate: string;           // ISO 8601, e.g., "2026-06-15"
  refreshCadence: string;          // "annual", "quarterly", "monthly", "on-demand", "as-needed"
  nextCheckDate: string;           // ISO 8601, when next refresh check is due
  isStale?: boolean;               // true if now > nextCheckDate
  methodologyUrl: string;          // Link to Methodology Card
  sourcesLimitsUrl: string;        // Link to Sources & Limits / caveats
}
```

### 1.3 Implementation Reference

A working reference implementation is available in `output/data-currency-badge.tsx` and `output/data-currency-badge.css`:

- **Component logic:** Formats dates, derives stale/current status, renders accessible HTML with semantic roles.
- **Styling:** Supports light and dark themes via CSS custom properties (e.g., `--color-border-subtle`, `--color-bg-subtle`).
- **Accessibility:** Uses `role="complementary"`, `aria-label`, semantic headings, and sufficient color contrast.

### 1.4 Integration Points

In each explainer artifact (generated by the derivation pipeline):

1. **Import the component:**
   ```tsx
   import { DataCurrencyBadge } from "@hee-lee-oss/toolkit";
   ```

2. **Pass explainer metadata:**
   ```tsx
   <DataCurrencyBadge
     retrievalDate={explainerMetadata.dataVintage.retrievalDate}
     refreshCadence={explainerMetadata.refreshCadence}
     nextCheckDate={explainerMetadata.nextCheckDate}
     isStale={isStale(explainerMetadata.nextCheckDate)}
     methodologyUrl="/methodology"
     sourcesLimitsUrl="/sources"
   />
   ```

3. **Display placement:** Near the top of the artifact (after title) or in a sidebar; must be visible without scrolling on first load.

### 1.5 Testing

The component should be tested for:
- [ ] Correct date formatting across locales (en-US default, extensible).
- [ ] Stale/current status calculation.
- [ ] Accessible rendering (axe, WCAG 2.2 AA compliance).
- [ ] Light and dark mode switching.
- [ ] Mobile responsiveness.

## 2. Drift Detection Integration

### 2.1 Module Location (in toolkit-002)

The drift detection utilities should be committed to:

```
packages/toolkit/
  src/
    drift-detection/
      core.ts                      # Core detectDrift() function
      adapters/
        bls-cpi.ts                # BLS CPI API adapter
        usda-nass.ts              # USDA NASS adapter
        gtfs.ts                   # GTFS feed adapter
        osm.ts                    # OpenStreetMap adapter
        college-scorecard.ts       # College Scorecard adapter
        base.ts                   # Base adapter interface
      types.ts                    # Shared TypeScript interfaces (DriftReport, etc.)
      README.md                   # Drift detection documentation
```

### 2.2 Core Function Specification

```typescript
interface DriftReport {
  explainerId: string;
  hasDrift: boolean;
  reason?: string;                // e.g., "version mismatch", "refresh cadence exceeded", "api error"
  currentVersion?: string;        // Current version reported by the source
  recordedVersion?: string;       // Version in explainer-metadata.json
  checkDate: string;              // ISO 8601 timestamp of the check
}

async function detectDrift(
  explainerMetadata: ExplainerMetadata,
  options?: { verbose?: boolean; timeout?: number }
): Promise<DriftReport>;
```

### 2.3 Source Adapter Interface

Each source adapter must implement:

```typescript
export interface SourceAdapter {
  /**
   * Check if the source has a new version or update available.
   * @param sourceUrl The URL of the data source
   * @param recordedVersion The version currently recorded in explainer-metadata.json
   * @returns VersionCheckResult
   */
  checkVersion(sourceUrl: string, recordedVersion: string): Promise<VersionCheckResult>;

  /**
   * Optional: download the latest snapshot and compute its hash.
   * @param sourceUrl The URL of the data source
   * @param outputPath Where to save the snapshot
   * @returns The SHA-256 hash of the downloaded file
   */
  downloadSnapshot?(sourceUrl: string, outputPath: string): Promise<string>;
}

interface VersionCheckResult {
  hasUpdate: boolean;
  currentVersion?: string;
  currentDate?: string;
  error?: string;
}
```

### 2.4 Implementation Reference

A working reference implementation is available in `output/drift-detection.ts`:

- **Core logic:** Queries source adapters, compares versions, checks refresh cadence.
- **Error handling:** Graceful fallback if API is unreachable; logs errors.
- **Pluggable adapters:** Each source type has its own adapter module.

### 2.5 CI Integration

In the toolkit's CI workflow (GitHub Actions), add a scheduled drift-detection job:

```yaml
name: Drift Detection
on:
  schedule:
    - cron: "0 9 1 * *"  # First day of each month at 9 AM UTC
  workflow_dispatch:     # Allow manual trigger

jobs:
  detect-drift:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
      - name: Install dependencies
        run: pnpm install
      - name: Run drift detection
        run: |
          pnpm run detect-drift \
            --explainers-dir ./explainers \
            --output drift-report.json
      - name: Create GitHub issues for drift
        if: failure()
        run: |
          pnpm run create-refresh-issues \
            --drift-report drift-report.json \
            --project "open-data-explainers"
      - name: Upload report
        uses: actions/upload-artifact@v3
        with:
          name: drift-report
          path: drift-report.json
```

### 2.6 CLI Usage

When integrated into toolkit-002, drift detection should be available as:

```bash
# Check all explainers for drift
pnpm run detect-drift

# Check a specific explainer
pnpm run detect-drift --id county-ag-ne-2026

# Output a report
pnpm run detect-drift --output drift-report.json

# Create refresh tasks/issues automatically
pnpm run detect-drift --create-issues
```

### 2.7 Testing

Adapters should be tested for:
- [ ] API mocking and error cases (timeout, 404, invalid JSON).
- [ ] Correct version detection across all supported sources.
- [ ] SHA-256 hash computation for snapshot files.
- [ ] Graceful degradation if source API changes.

## 5. Maintenance & Future Extensions

### 5.1 Adding a new source adapter

1. Create `packages/toolkit/src/drift-detection/adapters/new-source.ts`.
2. Implement the `SourceAdapter` interface.
3. Register the adapter in `packages/toolkit/src/drift-detection/core.ts`.
4. Add tests in `packages/toolkit/src/drift-detection/adapters/__tests__/new-source.test.ts`.
5. Document the adapter in `packages/toolkit/src/drift-detection/README.md`.

### 5.2 Updating the badge design

If the data-currency badge design is refined:

1. Update the component in `packages/toolkit/src/components/data-currency-badge/`.
2. Update the CSS for light/dark mode consistency.
3. Increment the component version and update the changelog.
4. Re-run tests and component story (if Storybook is used).

### 5.3 Monitoring drift detection failures

When drift detection adapters fail (e.g., API changes), the toolkit maintainer should:

1. Review the error log from the failed CI job.
2. Update the corresponding adapter to match the new API.
3. Add regression tests to prevent recurrence.
4. Open a maintenance task if the fix is not trivial.
